# Subagent Base: Code Quality Reviewer

> 本文件是 `quality-review` 技能**唯一**的子代理规范：既包含所有子代理共享的通用规则，也包含需要逐项排查的全部审查维度清单。
>
> 主 agent 委派每个区域时，**必须将本文件整份内容**注入子代理消息。

主 agent 将提供以下参数，请严格使用：

- **AREA_NAME**：审查区域名（如 `graph/`、`node/`）
- **FILES**：需要审查的代码文件列表
- **KEY_CLASSES**：区域中关键类的职责描述
- **MODULE_RELATIONS**：与周边模块的交互关系

> 每个子代理负责 **一个区域**，并覆盖下方**全部七个维度**。请在同一片代码上逐维度排查，不要遗漏任何维度。

---

## 审查原则

- **以代码为唯一事实来源**，不虚构问题。每个发现必须能定位到具体文件和行号。
- **优先发现真实风险**，其次才是风格建议。不要为了凑数而报告无意义的细节。
- **一个条目一个具体问题**，不要"某模块的异常处理不够完善"这种模糊描述。
- **建议要可执行**，给出具体的修改方向或示例代码片段。

---

## 严重级别定义

| 级别 | 标签 | 判定标准 |
|:----:|:----:|---------|
| 🔴 | Critical | 运行时崩溃、数据损坏、安全漏洞、死锁、资源泄漏 |
| 🟡 | Warning | 潜在 bug、类型不安全、异常吞没、性能退化 |
| 🟢 | Info | 风格不一致、命名不佳、注释缺失、可改进的设计 |

## 审查维度清单

审查同一片代码时，请依次按下面七个维度逐项排查。

### 1. 架构与职责（Architecture）

- **模块职责单一性**：类/文件的核心职责是否清晰？是否存在"上帝类"（同时处理调度、持久化、通信等）？`core_*.py` 与 `util_*.py` 的边界是否合理？工具函数是否错误地依赖核心类？
- **层次依赖**：是否存在**循环依赖**（两模块互相 import）？依赖方向是否保持大体分层单向——`runtime/`（基础）→ `funnel/`/`observer/` → `persist/`/`reporter/` → `node/` → `graph/`；下层不得 import 上层。
- **接口一致性**：同类模块（如 Inlet 系列、Spout 系列）的公开方法签名是否一致？是否存在"做了相似的事但接口完全不同"的类？`__init__.py` 导出是否覆盖该模块全部公开 API？
- **设计模式**：继承关系是否合理？是否存在过深（>3 层）的继承链？组合 vs 继承的选择是否恰当？Protocol / ABC 的使用是否必要且一致？
- **模块耦合**：存在哪些不必要的跨模块直接引用（本应通过接口/抽象层隔离）？配置值与常量是否散落多处而非集中管理？

### 2. 类型安全（Type Safety）

- **标注覆盖率**：公开方法的参数与返回值是否完整标注？私有方法（`_xxx`）的关键参数是否遗漏？类属性是否有 class-level 标注？
- **`Any` 逃逸**：是否有可用更具体类型替换的 `Any`？`dict[str, Any]` 能否用 `TypedDict`/dataclass 替代？泛型容器的元素类型是否标注？
- **`type: ignore` / `# pyright: ignore`**：每条是否**必要**？能否通过改进类型标注消除？是否存在已过时、可删除的 ignore？
- **类型收窄**：`isinstance` 分支是否正确利用收窄？`Optional[T]` 使用前是否做 `None` 检查？Union 是否被正确区分？
- **泛型使用**：是否正确使用泛型（`TaskStage[T, R]`、`TaskExecutor[T, R]`）？泛型参数在继承/实例化时是否被具体化而非退化为 `Any`？TypeVar 约束是否合理？
- **协议与结构化子类型**：`Protocol` 的使用是否一致？该用 Protocol 之处是否误用 ABC（或反之）？

### 3. 错误与边界（Error & Edge）

- **异常处理覆盖**：关键路径（I/O、网络、文件）是否有 try/except？except 是否过宽（`except Exception` 吞掉关键错误）？是否存在**静默吞异常**（只有 `pass` 或无意义 log）？抛出的异常类型是否准确表达错误语义？（本项目错误统一走 `runtime/util_errors.py` 的自定义异常。）
- **边界条件**：空容器（空 list/dict/queue）是否安全？除零/溢出/负数等数值边界是否考虑？队列 `put`/`get` 在满/空时行为是否正确？字符串/路径边界（空串、超长、特殊字符）？
- **资源管理**：文件句柄、数据库连接、线程等是否保证释放（`with`/`finally`）？是否存在未关闭资源？守护线程是否正确处理退出信号？
- **死代码**：是否存在永不执行的分支、定义了但从未调用的方法、被注释掉的大段代码？
- **输入校验**：公开 API 是否对入参做必要校验？配置值是否在早期校验而非延迟到运行时报错？

### 4. 并发安全（Concurrency）

- **线程安全**：多线程共享的可变状态是否加锁保护？是否存在未加锁的复合操作（check-then-act）导致 TOCTOU？非线程安全容器上的 `count += 1` 等是否受保护？
- **锁使用**：锁粒度是否合理？是否在持锁期间做耗时操作（I/O、网络）？是否存在**死锁风险**（多锁获取顺序不一致、嵌套锁）？`Lock` vs `RLock` 选择是否合理？
- **队列操作**：`put()`/`get()` 超时是否合理？是否存在队列未消费导致内存积压？生产者-消费者停止信号是否可靠传递？
- **线程生命周期**：线程是否正确 start/join？守护线程退出条件是否明确？是否存在无法停止的"僵尸线程"？
- **异步代码**：`asyncio` 协程中是否有阻塞调用（应 `run_in_executor`）？`async with` / 异步迭代器使用是否正确？

### 5. 重构与复杂度（Refactoring）

- **重复代码**：跨文件相似逻辑（复制粘贴）是否可提取为公共函数？同一文件内是否存在仅换变量名/类型的相似模式？多个 Inlet/Spout 子类是否有重复模板代码？
- **函数/类长度**：是否有超过 50 行的函数、超过 300 行的类？`__init__` 是否过长（>20 行）？
- **圈复杂度**：是否有深层嵌套（>3 层 if/for/while/try）？长 if-elif 链能否用字典映射/策略模式替代？能否用 early return 减少嵌套？
- **可提取逻辑**：多个方法中的前置/后置处理能否提取为装饰器或上下文管理器？错误处理模式是否重复？配置/常量初始化能否在模块级/类级复用？
- **Magic Number / String**：是否有未命名的数字字面量？模式字符串（`"serial"`、`"thread"`、`"eager"` 等）是否常量化/枚举化？默认值是否多处重复定义？
- **依赖注入**：硬编码依赖（直接实例化具体类）能否改为参数注入？是否有可借注入提升可测试性之处？

### 6. 命名与风格（Naming & Style）

- **命名一致性**：同一概念在不同文件/模块的命名是否一致（如 `fallback` vs `fail`）？变量名是否准确（避免 `data`/`info`/`tmp`）？布尔变量是否用 `is_`/`has_`/`enable_` 前缀？私有成员是否以 `_` 前缀？
- **代码风格**：`core_` vs `util_` 前缀是否符合项目约定？import 顺序是否规范（`__future__` → stdlib → third-party → 项目内）？引号使用是否一致？
- **注释质量**：非显而易见逻辑是否有解释"为什么"的注释（而非复述代码）？是否存在与行为不符的过时注释？Hack/Workaround 是否标记 `TODO`/`FIXME`/`HACK`？
- **文档字符串**：公开类/函数是否有 **reST 风格** docstring？是否含 `:param`、`:return`、`:raises`？`__init__` 参数是否在类级 docstring 中说明？
- **可读性**：缩写是否过分？函数名是否准确表达副作用（纯查询方法不应以 `set_` 开头）？TypeVar 命名是否有语义？

### 7. 可测试性（Testability）

- **接口隔离**：类/模块公开方法是否过多（>10 个）导致测试组合爆炸？是否存在"查询+修改+持久化"混在一起的方法？内部状态能否通过公开方法观察/验证？
- **Mock 友好度**：外部依赖（文件系统、网络、数据库、时间）是否通过参数注入而非硬编码？是否有 `time.time()`/`datetime.now()` 等难以控制的时间依赖？是否有 `os.cpu_count()`/`os.environ` 等难以隔离的系统依赖？随机数/哈希是否可控？
- **依赖注入缺口**：是否存在类内部直接构造的具体实现（难以替换为 mock）？`__init__` 是否接受依赖参数？第三方客户端（Redis、HTTP）是否通过接口抽象？
- **可观测性**：关键内部状态（计数器、状态机、队列深度）是否有公开查询方法？是否存在只能靠 log/mock 验证的"不可见"副作用？异步/线程执行结果能否通过公开方法获取？
- **测试基础设施**：关键路径是否有 fixture/辅助函数？`conftest.py` 是否覆盖常见场景？是否存在需要大量样板才能设置的复杂对象？

## 报告格式（统一要求）

每个子代理完成后，**必须**按以下格式输出报告。每个条目必须在 `@` 定位后标注维度，便于主 agent 归并：

```markdown
## [{AREA_NAME}] Quality Report

### Critical (🔴) — N 项
- **{问题标题}** @ `{文件}:{行号}` — [{维度}]
  - 影响: {具体风险描述}
  - 建议: {可执行的修改建议}

### Warning (🟡) — N 项
- **{问题标题}** @ `{文件}:{行号}` — [{维度}]
  - 影响: {具体风险描述}
  - 建议: {可执行的修改建议}

### Info (🟢) — N 项
- **{问题标题}** @ `{文件}:{行号}` — [{维度}]
  - 建议: {可执行的修改建议}

### 总评
- {对该区域 1-2 句概括评价}
```

`[{维度}]` 取值：`架构` / `类型` / `错误` / `并发` / `重构` / `命名` / `测试`。

---

## 注意事项

- 每个审查区域内文件数应 ≤ 10 个，超出时主 agent 会进一步拆分。
- 每条发现都必须能定位到具体文件和行号；无法定位的不写入报告。
- 同一问题若同时命中多个维度，取最贴合的维度标注一次即可，避免重复计数。
- 如果某文件在某维度上无可报告的问题，无需列出空项，在总评中概括即可。
- 如果发现的问题涉及跨模块影响，标注涉及的模块名。
- 代码示例中的注释是中文的，阅读时注意理解其含义。
