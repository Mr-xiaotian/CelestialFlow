# bench/bench_observer.py

> 📅 最終更新日: 2026/11/13

## 目的

同一バッチのタスクに対して、`TaskExecutor` を **オブザーバーなし**、**print ログ**（フレームワーク内蔵の `PrintObserver`、構築時に `name` プレフィックスの指定が必要）、**tqdm プログレスバー**（`TqdmObserver`、`bench_observer.py` 内で定義）の 3 つのシナリオで実行し、所要時間を比較することで、オブザーバーのコールバックがもたらすパフォーマンスオーバーヘッドを定量化します。

ユーザーがタスクの規模やリアルタイムフィードバックのニーズに応じて、適切な監視戦略を選択できるように支援します。

## テスト内容

### オブザーバー方式の比較

| シナリオ | オブザーバー | 説明 |
|----------|--------------|------|
| **オブザーバーなし** | `None` | 生のエグゼキューター。コールバック出力なしで、ベースラインとなる |
| **print ログ** | `PrintObserver` | 統一された `on_event` でイベント種別（ノードの開始/終了、タスクの入力 / 成功 / 失敗 / スキップ）に応じて `name` プレフィックス付きの統計行を出力し、シンプルなログ出力をシミュレートする |
| **tqdm プログレスバー** | `TqdmObserver` | 統一された `on_event` で同じ組のイベント種別に応じて `tqdm` プログレスバーを更新し、視覚的なフィードバックを提供する |

### タスク負荷

計算量の異なる 2 種類のフィボナッチタスクを使用します：

```python
# 軽量タスク：fib(20~29)、計 10 タスク
light_tasks = list(range(20, 30))

# 「やや重い」タスク：fib(50, 55, 60, 65, 70, 75, 80)、計 7 タスク
# 注意：fibonacci は反復 O(n) 実装であり、fib(80) でも約 80 回のループにすぎず、単一タスクは依然としてマイクロ秒オーダー
heavy_tasks = [50, 55, 60, 65, 70, 75, 80]
```

## 主要パラメータ

| パラメータ | 値 | 説明 |
|------------|-----|------|
| `execution_mode` | `serial` | すべてのシナリオで直列モードを使用し、変数を制御してオブザーバーの影響のみを観察する |
| `max_workers` | 1 | 単一ワーカーで、並列スケジューリングの干渉を避ける |
| `max_retries` | 0 | 再試行せず、再試行ロジックによる追加のオーバーヘッドを除外する |

## 主要関数

### `run_benchmark`

```python
def run_benchmark(
    name: str,
    task_data: list[Any],
    func: Any,
    *,
    observer: Observer | None = None,
) -> float
```

`TaskExecutor(name, func, execution_mode="serial", max_workers=1, max_retries=0)` を構築し、
`observer` が渡された場合は `executor.add_observer(observer)` を呼び出したうえで、`time.perf_counter()`
で `executor.run(task_data)` を囲んで所要時間（秒）を返す。呼び出しごとに新しいエグゼキューターを作成し、状態の残留を避ける。

### `TqdmObserver`

`TqdmObserver` はフレームワークの `Observer` 基底クラスを継承し、統一エントリ `on_event(event: Event)` のみをオーバーライドし、
`match event` でイベント種別ごとにディスパッチする（`handle_exception` は基底クラスのデフォルト実装のまま）：

| イベント | 動作 |
|------|------|
| `NodeStartEvent` | その時点で累積された `_total` を用いて `tqdm(total=...)` を生成する |
| `TaskInputEvent` | `_total += 1`。プログレスバーが生成済みの場合は `total` を同期的に拡張して `refresh()` する |
| `TaskSuccessEvent` / `TaskFailEvent` / `TaskSkipEvent` | 共通の `_advance(1)` で進捗を進める |
| `NodeEndEvent` | プログレスバーを閉じる |

表にない `TaskRetryEvent`、終了シグナルイベント、グラフイベントはいずれの分岐にも該当せず、`match` により自然に無視される。
`Observer` 基底クラスは現在 `on_event` と `handle_exception` のみを提供し、`on_node_start` / `on_task_success` などのイベント別コールバックは存在しない。

### ワーカー関数

- `fibonacci(n)`：**反復**実装（`O(n)`）で、再帰ではない。`n <= 0` は `ValueError`、`int` 以外は `TypeError` を送出
- `cpu_intensive(x)`：純粋な CPU ループで、オブザーバーのオーバーヘッドを増幅するために使用。**現在のスクリプトではどのシナリオでも呼び出されていない**

## 発生しうる問題

1. **print の TTY バッファ**：`print()` はデフォルトで行バッファリングされ、実際のターミナルに出力する際に画面更新が発生し、ファイルへリダイレクトするより遅くなる可能性があります。ターミナル環境によって print のオーバーヘッドは異なる場合があります。
2. **tqdm の `total` 遅延生成**：`TqdmObserver` は `NodeStartEvent` を受信したときにプログレスバーを生成し、`TaskInputEvent` を受信したときに総量を加算する（このイベントは `NodeStartEvent` より先に到着する可能性があるため、プログレスバー未生成時には `_total` のみを加算する）。`run()` は先に全タスクを注入してからノードを起動するため、`NodeStartEvent` 到達時点の `total` には起動前に注入されたタスク数が既に含まれている。その後さらに `TaskInputEvent` があればプログレスバーは動的に拡張されるが、ベンチマーク結果の正確性には影響しない。
3. **ウォームアップ効果**：初回実行はバイトコードキャッシュのウォームアップ、import 初期化、システムキャッシュの影響を受ける可能性があり、後続ラウンドはより高速になります。`bench_observer_multirun()` は複数ラウンドの平均値を取ることでこの問題を緩和しています。
4. **フィボナッチ負荷自体が軽すぎる**：`fibonacci` は反復 `O(n)` 実装であり、`light_fib` と `heavy_fib` の単一タスク所要時間はいずれもマイクロ秒オーダーである。測定された総所要時間は主にフレームワークのスケジューリング、イベント配信、オブザーバー I/O で構成され、計算ではない。2 組のデータの差は主にタスク数（10 対 7）に由来し、`heavy_fib` を「計算が支配的」と解釈してはならない。オブザーバーのオーバーヘッドが単一タスクの所要時間に応じて減衰する様子を観察するには、真のミリ秒級負荷（再帰 fib や `time.sleep` の追加など）に置き換える必要がある。

## ベンチマーク結果（実測）

> 🟢 本セクションの各表の所要時間は過去の実測データであり、ソースコードからは検証できないため、手動で確認する必要があります。
>
> これらのデータは、オブザーバーがまだイベント別コールバックを使用していた旧バージョンで収集されたものである。現在の実装は `on_event` + `match` に統一されており、
> イベント配信のオーバーヘッドと相対比率は変化している可能性があるため、ローカルで再実行したうえで引用することを推奨する。

### 2026/07/30 - ローカル実測

> 環境: macOS、Python 3.14、`execution_mode=serial`

#### 単一ラウンド比較

| タスク | モード | 所要時間 | オブザーバーなしとの相対比 |
|--------|--------|----------|---------------------------|
| light_fib (10 tasks) | **オブザーバーなし** | 0.0037s | — |
| light_fib (10 tasks) | **print** | 0.0019s | -48.1% |
| light_fib (10 tasks) | **tqdm** | 0.0056s | +51.1% |
| heavy_fib (7 tasks) | **オブザーバーなし** | 0.0014s | — |
| heavy_fib (7 tasks) | **print** | 0.0014s | +2.6% |
| heavy_fib (7 tasks) | **tqdm** | 0.0014s | +0.9% |

> ⚠️ 軽量タスク（fib 20~29）は 1 回あたりの計算が非常に高速（マイクロ秒オーダー）なため、所要時間のばらつきが大きく、print シナリオで負の値が出るのは測定ノイズです。結論は平均値を参照してください。

#### 複数ラウンド平均（5 ラウンド、light_fib）

| モード | 平均値 | 最小値 | 最大値 |
|--------|--------|--------|--------|
| **オブザーバーなし** | 0.0015s | 0.0014s | 0.0017s |
| **print** | 0.0017s | 0.0016s | 0.0018s |
| **tqdm** | 0.0017s | 0.0017s | 0.0018s |

**主な結論**：

- 直列モードでは、測定値は主にフレームワーク自身のスケジューリングとイベント配信のオーバーヘッドで構成される。`fibonacci` は反復 `O(n)` であり、`fib(50~80)` でも数十回のループにすぎないため、「軽量」と「やや重い」の 2 組で単一タスクの計算量の差はどちらもマイクロ秒オーダーである。
- **軽量タスク**では、オブザーバーによる**相対的な差**がより顕著に現れる（過去の単一ラウンドデータでは ~50% に達した）が、その方向は安定していない（print では負の値も現れた）。絶対的な所要時間はミリ秒オーダーにすぎず、単一ラウンドの数値は測定ノイズに支配されるため、複数ラウンドの平均値を基準とすべきである。
- **やや重いタスク**（fib 50~80）では 7 タスクの総所要時間がむしろ低いが、これは主にタスク数が少ないためであり、「計算時間が支配的」だからではない。本スクリプトの 2 組の負荷はいずれも軽すぎるため、「単一タスクが 1ms を超えるとオブザーバーのオーバーヘッドは無視できる」という結論を導くことはできない。
- 実際の業務負荷におけるオブザーバーのオーバーヘッドを評価する必要がある場合は、ミリ秒以上の単一タスク所要時間に切り替えたうえで、3 つのシナリオを比較すべきである。

## 実行方法

```bash
python bench/bench_observer.py
```

## パラメータ調整

### 特定のテストシナリオを単独で実行する

`bench_observer.py` の `main()` で、単一ラウンド比較または複数ラウンド平均テストのいずれかを選択できます：

```python
def main():
    # 単一ラウンド比較のみを実行
    bench_observer_overhead()

    # 複数ラウンド平均のみを実行
    # bench_observer_multirun()
```

変更後に実行：

```bash
python bench/bench_observer.py
```

### タスク規模をカスタマイズする

`bench_observer_overhead()` または `bench_observer_multirun()` 内のタスクリストを変更します：

```python
# より大きな計算量を使用してオブザーバーのオーバーヘッド比率を観察する
heavy_tasks: list[Any] = list(range(80, 90))  # fib(80)~fib(89)

# より多くの軽量タスクを使用する
light_tasks: list[Any] = list(range(10, 50))  # 40 個の軽量タスク
```

### データ量と実行ラウンド数を調整する

```python
# bench_observer_multirun() 内でラウンド数を変更する
runs = 10  # 5 から 10 に変更し、より安定した平均値を取得する
```
